## Findings and resolutions

### Metadata completion did not recover a blocked CI decision

The real CI completion could be blocked while a metadata-only run was pending.
The later metadata completion was discarded because its ID was different from
the latest actual validation. An already-green Ready reporter needed no refresh,
so recovery waited for another reconciliation event.

`409a641` recognizes a fully authenticated `(run, attempt)` as a reconciliation
wake-up. It then proves the current full CI and native Ready again; the no-op is
never success evidence. Regression controls cover initially armed/unarmed PRs,
duplicate notifications, missing/failed/cancelled/pending real CI, pending Ready,
standby, forged/foreign/unlisted events, stale attempts and changed provenance.
A later test covers a genuine metadata rerun, rejection of its stale first
attempt, and cancellation after real CI subsequently fails. All mutations in
these tests use API fixtures, not GitHub.

### Release label casing could select a weaker plan

Native workflow comparisons recognized `Release-Validation`, but the Python
planner selected the fast lane for that spelling. The failing control was a
policy-only diff: the native event started CI but the plan omitted full gates.
`df3fed2` makes the planner's reserved-label match case-insensitive and tests
lower/mixed/uppercase labels plus distinct-name controls. The expression test
adapter also follows [GitHub's documented string comparison semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions).
The actual repository label was lowercase at review time; no live downgrade was
claimed or induced.

### Pages notifications shared a deployment queue

The entire Docs workflow used `pages` concurrency even when its artifact job
would be skipped. GitHub's default queue can replace a pending item, so unrelated
completion notices should not enter the deployment queue. `e90bd36` filters the
originating branch to main and puts concurrency on the artifact-backed deployment
job. The event matrix permits successful main pushes and verified recovery
dispatches, while rejecting PR, queue, ordinary manual, failed, foreign and
non-main notifications. This removes the routing overlap; actual hosted ordering
was not reproduced locally. See [GitHub concurrency semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency).

### Resource limits and workflow lint

`6a66b11` adds explicit timeouts to the remaining runner jobs and runs actionlint
inside the existing required policy job, without creating another runner job.
The bounds retain generous headroom over the historical successful sample; they
must be revisited against hosted distributions if legitimate runs approach them.

The linter release and archive SHA-256 digests are pinned. Downloads are bounded
to 20 MiB and only the verified regular executable is extracted. Host-dependent
shellcheck/pyflakes integrations are disabled. Initial review found that a global
diagnostic ignore could also cover a new `queue` in YAML flow syntax. The final
implementation instead matches the exact file, line, column, kind and message
for the three reviewed coordinator queues. A real actionlint run accepted the
unmodified control and rejected an additional invalid flow-syntax queue. Unit
controls cover tampered archives, symlinks, changed queue values/locations,
duplicates, missing diagnostics and fatal tool results.

The original API-checker ownership, empty-target coordinator and manual-ref
improvements remain intact. Swift 6.2 compiler validation, local/release default
API checks, coverage, consumers, sanitizers, SDKs and exact-SHA release gates
retain their distinct owners.

## Hosted metadata verification — PR #51

An actual PR description edit exposed one representation difference from local
fixtures: GitHub records a skipped dynamic aggregate name as the expression
source without `${{ }}`, rather than its evaluated display name. The original
metadata verifier rejected this valid no-op. The fix recognizes only the exact
reviewed native expression in addition to its evaluated name, retaining every
workflow/merge/attempt/job/check binding. Workflow-derived inventory tests now
cover all combinations, with forged expressions rejected.

Read-only execution of the corrected verifier against live GitHub API evidence
accepted metadata runs **37025028284, 37026225937** (attempt 1), accounting for
**32 native skipped checks**. The original real CI run **37024738252** remained
queued and was not cancelled. No metadata run allocated an execution job or
published either a CI success proof or a protected aggregate under its required
name. These observations bind to the first PR candidate; the workflow YAML is
unchanged by this verifier correction. Full final-candidate CI, genuine bot
arming/recovery after merge and realized timing savings remain unverified.

## Follow-up: native required checks after metadata events

The initial zero-runner metadata design preserved historical checks in the REST rollup, but GitHub evaluated the latest workflow suite and displayed required checks as Expected. A passing historical rollup was therefore insufficient evidence of merge readiness.

Required aggregate names now stay fixed. Metadata events share the validation concurrency group without cancelling its running validation; after it completes, only the Ubuntu aggregate runs. It re-reads the latest actual validation and requires the exact PR head, base, merge commit, validation-label set, native GitHub Actions check, and unchanged attempt. The original required job must have completed within the last 24 hours; metadata edits cannot indefinitely renew old validation. Failed, cancelled, pending, stale, missing or raced evidence cannot produce success. Metadata gates are excluded from Dependabot/main reuse selection; those policies still require the original full validation inventory. Metadata events use GitHub's max queue without cancellation so they do not replace pending real validation. Validation-affecting events retain the single queue and cancellation to supersede obsolete work. GitHub bounds the max queue at 100 waiting runs; failed or cancelled validation still fails closed.

Hosted acceptance requires both the final-head real CI and a subsequent description-edit event to pass, with the actual PR merge state no longer reporting Expected checks. No merge or release is performed by this follow-up.
