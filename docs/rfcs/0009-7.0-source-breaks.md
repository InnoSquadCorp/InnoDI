# RFC 0009 — 7.0 source breaks

- **Status**: Accepted
- **Authors**: InnoDI maintainers
- **Created**: 2026-09-29
- **Last updated**: 2026-09-30
- **Accepted**: 2026-09-30, explicit repository-owner approval for 7.0.0
- **Target release**: 7.0.0
- **Tracking plan**: [7.0.0 post-audit plan](../plans/7.0.0-post-audit.md), items G1, M1, M2, and M4

## Summary

InnoDI 7.0 takes four source-breaking changes on one major train:

| Item | Change | State |
|---|---|---|
| G1 | Parent key paths are spelled `\Self.member` | Implemented |
| M1 | `InnoDISwiftUI` stops re-exporting SwiftUI | Implemented on the train |
| M2 | macOS 14 floor, and the SwiftUI host owner moves to Observation | Implemented on the train |
| M4 | `ContainerRole` returns to an enum | Deferred to 8.0 |

Each change ships with an `InnoDI-Migrate` rule or a mechanical migration
step. Evidence below comes from the pilot applications InnoSample, BlPia,
Lynceus, and Mulbyul, which were read but not modified.

## G1 — Canonical parent key paths

Implemented on the train. The macro rejects a named root such as
`\AppContainer.config` with `sub.noncanonical-parent-key-path` and a fix-it.
The macro and build validation reject nested components, `InnoDI-Migrate`
blocks them, and the graph CLI records no edge for them. `InnoDI-Migrate`
rewrites named roots. InnoSample's `AppContainer` uses a named parent root, so it needs this
rewrite. See the 6.x → 7.0 section of the migration guide.

## M1 — Stop re-exporting SwiftUI

### Problem

`InnoDISwiftUI` declares `@_exported import SwiftUI`. Every file that imports
`InnoDISwiftUI` therefore sees all of SwiftUI, whether or not it asked for
it. A dependency graph tool or a reviewer cannot tell from a file's imports
that it uses SwiftUI, and a module that only needs the environment bridge
still pulls SwiftUI's names into scope.

### Proposal

Replace the re-export with an ordinary `import SwiftUI`. Keep
`@_exported import InnoDI`, because `InnoDISwiftUI`'s public API is built on
InnoDI types.

Generated feature-root helpers and environment bridges spell `SwiftUI.View`,
`SwiftUI.ViewModifier`, and `SwiftUI.EnvironmentValues`. A module qualifier
only resolves when the file imports that module, so every file that uses
those helpers must import SwiftUI itself after this change.

### Evidence

- InnoSample's `AppContainer.swift` and Mulbyul's `AppContainer.swift` import
  `InnoDISwiftUI` without `SwiftUI` and use `@SubContainer(featureRoot:)`.
  Both would stop compiling without a migration.
- Lynceus imports SwiftUI next to `InnoDISwiftUI` and is unaffected.
- BlPia does not import `InnoDISwiftUI`.

### Migration

`InnoDI-Migrate` gives every file that imports `InnoDISwiftUI` a full
`import SwiftUI` with the same visibility: the access level and `@_exported`
attribute of the `InnoDISwiftUI` import. It raises an existing unconditional
`import SwiftUI` when that import grants less, and a scoped import or one in
another `#if` clause does not count. The rule is idempotent and reports each
change in `--check` and `--report`. An external consumer
fixture pins that a file importing only `InnoDISwiftUI` no longer sees
SwiftUI symbols.

## M2 — macOS 14 floor and Observation

### Problem

`DIContainerHostOwner` is an `ObservableObject` whose `phase` is
`@Published`, and `DIContainerHost` keeps it in `@StateObject`. The host
depends on Combine only for this, and SwiftUI's Observation framework is the
current model for view-owned state. Observation requires macOS 14, while the
package floor is macOS 13. Every other platform floor already includes
Observation: iOS 17, tvOS 17, watchOS 10, and visionOS 1.

### Proposal

- Raise the macOS floor to 14 in `Package.swift`, the external consumer
  fixtures, the documentation snippet package, and the generators that write
  package manifests.
- Make `DIContainerHostOwner` a `@MainActor @Observable public final class`.
  Remove its `ObservableObject` conformance, `objectWillChange`, and the
  `$phase` publisher. Only `phase` is observed; every other stored property,
  including the cached lifecycle handle, is `@ObservationIgnored`.
- Keep `DIContainerHost` in `@State` instead of `@StateObject`. The owner's
  initializer constructs nothing, so SwiftUI discarding an extra instance is
  harmless.
- Keep the committed-transition logic in `publish(_:)`. Observation calls an
  `onChange` handler before the value changes, as `@Published` did, so the
  owner must still decide from its committed transition and drain re-entrant
  starts after the current publication.

### Evidence

| Pilot | App macOS target | InnoDI pin |
|---|---|---|
| InnoSample | 15.0 | exact 5.1.0 |
| BlPia | 15.0 | exact 3.0.1 |
| Lynceus | 15.0 | exact 5.1.0 |
| Mulbyul | 15.0 and 26.0 | exact 5.1.0 |

BlPia sets `MACOSX_DEPLOYMENT_TARGET` to 12.0 only for its swift-syntax and
InnoFlow package targets, not for targets that link InnoDI. No pilot uses
`DIContainerHostOwner` or `DIContainerHost` directly, so the Combine removal
does not break a pilot.

### Migration

- Raise any macOS deployment target below 14 that links InnoDI.
- Replace `owner.$phase` and `owner.objectWillChange` subscriptions with
  `withObservationTracking`, or read `owner.phase` from a SwiftUI view.
- Replace `@StateObject var owner = DIContainerHostOwner(...)` with
  `@State var owner = DIContainerHostOwner(...)`.

No `InnoDI-Migrate` rule is proposed for M2, because each step depends on
the application's own deployment settings or observation code.

## M4 — `ContainerRole` enum, deferred to 8.0

`ContainerRole` is a string-backed token because an enum-typed argument on a
multi-role attached macro crashed the compiler. The informational compiler
canary compiles and runs on Swift 6.4. Swift 6.2 is the 7.0 minimum
toolchain, and its result is only available from the manual CI canary, which
has not run for this train. Changing the argument to an enum without that
evidence would reintroduce the crash for Swift 6.2 users, so M4 moves to 8.0.

## Alternatives considered

- **Generate InnoDISwiftUI-owned aliases instead of `SwiftUI.` qualifiers.**
  Generated code would then compile without `import SwiftUI`, but every
  generated helper and snapshot would change for a small convenience. The
  migration rule is simpler and keeps generated code stable.
- **Keep macOS 13 and make only the host owner conditional.** A
  platform-conditional owner type would split the public API by OS version.

## Acceptance criteria

- The migration rule adds `import SwiftUI` exactly once per affected file
  and is idempotent, with tests.
- A negative external consumer fixture fails when a file that imports only
  `InnoDISwiftUI` uses a SwiftUI symbol.
- The host reentrancy and capture-lifetime tests pass with Observation, and
  a test pins that redraws do not invalidate on handle creation.
- The public API baseline reviews the removed `ObservableObject` conformance
  and publisher as intended changes.
