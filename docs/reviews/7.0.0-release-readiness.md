# InnoDI 7.0.0 release preparation

This branch prepares the 7.0 API and its validation. It is not a published
release, and a successful pull request does not authorize a tag or release.
Keep the stable installation at 6.0.0 until the final candidate transition
described in [RELEASING.md](../../RELEASING.md).

## Source and release scope

- Published baseline: `6.0.0`, commit
  `249e26703ab285092fd717896e48bba2d87a4533`.
- Integration base: `c4ba6a489aced1e32c673d8388db0fae5cb63d6d`, including
  the CI event, reuse, and duplicate-validation repairs in PR #51.
- Previously qualified local feature state:
  `2814acd6164f7016e6a06949833a7022a5514cb0`. The seven feature/fix commits
  were replayed in order on the integration base. Production sources matched
  that state byte for byte immediately after integration.
- Included: dependency-order opt-in, typed synchronous prewarm, explicit owned
  async lifecycle, scoped `withPrepared`, typed override setters and validated
  presets, explicit MainActor override-isolation repair, duplicate-name macro
  validation optimization, and precise dependency/override recovery diagnostics.
- Excluded: MainActor shared-cell specialization, Set-to-Array caller tracking,
  inline caller representations, compact trace owners, and the ready-path guard.
  Their experimental timing results are not claims about this release.

The established source breaks from 6.0 are the macOS 14 floor, Observation host
owner, explicit SwiftUI import, canonical parent key paths, and the SwiftSyntax
604.0.0 dependency pin. Typed prewarm additionally replaces the generated throwing
key-path overload. The owned API is opt-in, but its view is a distinct nominal
type and generated names have documented collision rules. See the
[migration guide](../../Sources/InnoDI/InnoDI.docc/MigrationGuide.md) and
[owned-container contract](../../Sources/InnoDI/InnoDI.docc/OwnedContainers.md).
RFC 0008 and RFC 0009 are already Accepted for their async-on-demand and existing
source-break scope; they are not retrospective approval records for every new
macro-first API listed above. `ContainerRole` remains the existing
string-backed token; an enum conversion is not included.

## Evidence already obtained

These are completed Linux Swift 6.4 checks of the retained source, not Apple
qualification or a substitute for the PR's final-head checks:

- 640 executed macro/core passes; four opt-in tests skipped and one
  Darwin-dependent integration test excluded.
- 24 real-plugin negative fixtures with exact diagnostic positions and ten
  optimized repaired consumers; the repaired examples are bound to their docs.
- Nine exact-source override tests, two actor-isolation compile negatives, and
  the executable override documentation example.
- Public, owned, deferred, and prepared-operation consumers, including 25
  intended compile failures. Earlier lifecycle qualification includes success,
  preparation failure, operation failure, cancellation, cleanup cancellation,
  override bypass, and closed-view behavior.

The duplicate-name predicate optimization was separately qualified in ordinary
native SwiftPM consumer builds. A 100-provider consumer's single factory edit
was 6.83% faster in discovery and 7.92% faster in an independent holdout; both
fixed stages passed their primary, non-regression, and same-binary control
criteria. This is Linux Swift 6.4 evidence with prepared runtime/dependencies and
a prebuilt `-Onone/-g` macro executable. The edit rebuilt both consumer files.
It does not establish full-package, Apple, optimized-plugin, no-op, or runtime
speedups. The 20-provider edit holdout established non-regression only. The later
diagnostic wording changes were not re-timed.

## Final-head qualification still required

The exact PR head and applicable workflow attempt must be recorded before
marking any item complete. A compiled test bundle is not an executed suite.

- [ ] Full package/strict concurrency and coverage on the supported Apple lane
- [ ] Swift 6.2 package execution plus strict and external consumers; Swift
      6.3 and Swift 6.4 compatibility lanes
- [ ] Thread and address sanitizers, including lifecycle overlap tests
- [ ] SwiftUI, InnoDITesting, all examples, and declared Apple platform builds
- [ ] Apple-only async-on-demand capture and prepared-operation fixtures
- [ ] Full three-product public API contract reviewed and baseline refreshed
      from compiler output, then checked on the final head
- [ ] Documentation snippets, localization/link contracts, DocC, global DAG,
      automation policy, and the repository macro-performance gate
- [ ] Fresh exact-revision consumer and renamed-checkout/path-identity checks
- [ ] Actual minimum-OS execution where required by the release decision;
      generic platform compilation alone does not demonstrate this

The API checker may export the current compiler-normalized contract for review,
but it must continue failing on a mismatch. An exported candidate is evidence,
not an approved replacement baseline. Review additions, removals, defaults,
isolation, accessor capabilities, and relationships across all three products;
generated consumer APIs also require their real-plugin fixtures.

Preparation checks on the integrated branch passed 206 portable Python policy
and API-output tests, pinned actionlint 1.7.12 over all 12 workflows, action-pin
and validation guards, documentation links and English/Korean structure, and
prepared-fixture source parity. The repaired standalone runtime alias module
also compiled with strict concurrency and warnings as errors on Linux Swift
6.4. Three Apple/compiler-specific Python modules were excluded from that
portable run and remain in the actual Apple CI suite. These checks do not mark
any of the final-head Apple requirements above complete.

## Publication boundary

Before publication, finish the final version/README/migration metadata commit,
validate its exact SHA, and obtain a successful `Release Gate` run with
`publish=false` / `Candidate Required`. The final candidate must be on `main`
through the normal merge process. Verify the repository's immutable-release,
branch/tag ruleset, and release-environment controls at that time. Publishing
requires separate approval for that version and SHA; do not create a tag from
this preparation branch. No merge, tag, or release is performed by this task.
