## 수정 결과

1. **CR-F02 cache**: [ValidationSignature](../../Sources/InnoDIBuildSupport/ValidationSignature.swift)의 `collectWithMetrics`가 매번 실제 bytes를 읽고 hash를 확인한 후 digest를 재사용한다. 읽기 전후 metadata가 바뀌면 재시도를 요구하고, hash/parse는 같은 Data를 사용한다. manifest v7이 이전 레코드를 무효화한다. `metadata-hit`은 metadata와 content가 모두 같은 경우다.
2. **CR-F01 API gate**: [check-public-api.py](../../Tools/check-public-api.py)의 `declaration_contract`가 actor identity, isolation modifier, public setter 유무를 보존한다. schema 5의 324개 symbol에 metadata를 추가했으며 공개 symbol 집합을 변경하지 않았다. 새 metadata와 schema만 제외하면 이전 baseline과 동일하다.
3. **CR-F03 graph**: [DIAsyncScope](../../Sources/InnoDI/DIAsyncScope.swift)의 `makeTopologicalOrder`를 heap stack 기반 DFS로 바꿨다. 기존 순서/중복 edge/cycle path를 유지하며 임의 깊이 제한이나 새 public error를 도입하지 않았다.
4. **CR-U01 → 확정 결함**: TERM을 무시하는 직접 소유 child가 Doctor timeout 이후 살아남는 반례를 확인했다. [WorkspaceToolProcess](../../Sources/InnoDIWorkspaceAnalysis/WorkspaceToolProcess.swift)의 `runWorkspaceTool`을 Doctor/Graphviz에서 공유한다. process group을 만들고 leader PID를 reap 전까지 보존하여 정상/실패/timeout 후 그룹 정리를 수행한다. stdout/stderr는 각각 16 KiB raw-byte tail만 메모리에 유지한다. 잘못된 UTF-8의 replacement decoding은 표현 문자열 크기를 늘릴 수 있으나 입력 로그 전체를 저장하지 않는다.
5. **CR-O01 개선**: permanent close에서 scope 소유 operation을 해제한다. idle/ready/failed 상태의 factory-only capture는 scope가 살아 있어도 풀리고, 이미 실행 중인 operation 자신의 capture는 반환까지 유지된다. 기존 waiter cancellation/retry/closed 오류 계약은 유지한다.

프로세스 한계: Doctor 기본 timeout 300초, Graphviz 30초, TERM grace 200 ms 후 KILL. 시그널 종료는 `128 + signal`로 보고한다. 독립 세션/process group으로 이탈한 자손이나 부모의 강제 종료/전원 장애까지 정리하는 sandbox/guardian은 아니다. synchronous API에는 task-cancellation 인터페이스가 없으므로 그 축은 N/A다. 사용자의 작업이나 무관한 프로세스를 탐색해서 종료하지 않는다.

### 실패 분류와 재사용 제한

- **미확정 integration 관측 U02**: 첫 전체 실행에서 두 compile-fail fixture의 required structured plugin 진단이 빠지고 compiler 진단만 보였다. 최종 전체 새-scratch 실행은 모두 통과했다. 같은 accessor fixture의 실제 plugin fresh/reused build도 모두 원래 required code를 출력했다(`fix-plugin-fresh-diagnostic.log`, `fix-plugin-reused-diagnostic.log`, 의도된 compile-fail exit1). 첫 실행 도중 추가 source 변경과 기존 scratch 재사용이 있었지만 어느 쪽이 원인인지는 확정하지 못했다. 기대 진단을 optional로 낮추거나 기존 cache를 삭제하지 않았다. 재시도 통과를 근본 원인 해결로 주장하지 않으며, 확정 제품 결함 4건과 합산하지 않는다. 최종 게시 후보 CI에서 재관측해야 한다.
- 최초 cache CLI 점검은 `swift test`가 갱신하지 않은 이전 실행 파일(version6)을 사용했다. 이것은 수정 검증으로 채택하지 않았다. product를 명시적으로 다시 build한 version7 실행 파일로 valid/cached/fresh 대조를 반복했다. 이전 결과는 `fix-cache-cli-old-binary-*.log`에 남겼다.
