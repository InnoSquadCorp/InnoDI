## 1. 목표·범위·현재 사실

기존 여덟 개선 방향을 유지하면서 두 차례 감사의 **수정 항목 18개(F01–F12, N01–N06)와 미완료/검증 부족 항목 7개(G01–G07)**를 모두 추적한다. F12와 N05는 각각 둘 이상의 반례를 포함하므로 항목 수를 개별 결함 수나 완성도 비율로 사용하지 않는다.

확인된 사실:

- 작성 시 후보 HEAD는 감사 당시와 같고 promotion worktree는 계획 작성 전 clean이었다. 기존 지적을 해결한 변경은 아직 없다.
- 두 감사에서 기존 관련 테스트를 각각 193개, 103개 재실행해 통과했다. 겹치는 suite가 있으므로 296개의 고유 테스트로 합산하지 않는다.
- 새 반례는 Swift 6.4에서 별도로 컴파일/실행했으며 Swift 6.2·전체 플랫폼 재검증은 남아 있다. `--skip-build` 결과를 새 구현의 최종 검증으로 재사용하지 않는다.
- 실제 메모리 해제 실패, migration 루트 밖 쓰기, graph 계약 누락, host 종료 문제, mock 사전 검사·컴파일 문제 등이 재현됐다. 따라서 기존 문서의 “implementation complete”는 현재 배포 가능 판정 근거로 사용하지 않는다.

작업 가정과 제외 범위:

- 후속 실행 요청을 받으면 현재 promotion 후보를 출발점으로 삼되, 그때의 원격/로컬 상태와 사용자 변경을 다시 확인한다.
- **물별 원본은 테스트만 허용한다. 소스·설정·Package.resolved·프로젝트 생성물·Git 상태를 변경하거나 커밋하지 않는다.** 필요하면 승인 범위의 원본 revision을 격리 복제해 candidate를 주입하여 검증하고, 호환성 실패를 실패 그대로 기록한다. 원본 변경이 필요한 경우 별도 승인 없이는 적용하지 않는다.
- 다른 소비자 저장소도 우선 격리 검증하며 이 계획만으로 제품 migration 커밋을 허용하지 않는다.
- 최소 Swift/OS 버전 상승, concurrency 우회, validation opt-out, coverage/performance floor 완화, runtime registry 도입으로 문제를 피하지 않는다.
- 이 요청에서는 **계획 문서만 작성**한다. 구현·커밋·push·merge·tag·공개 배포는 실행하지 않는다. 후속 구현 요청과 실제 release 승인은 구분한다.

## 2. 순서와 의존성

| 단계 | 작업 | 목표 | 단계 완료 기준 |
|---|---|---|---|
| 0 | T24 | 기준선·영구 반례·설계 결정 | 25개 감사 ID가 재현 또는 부족한 증거에 연결되고 위험 설계 선택이 기록됨 |
| 1 | T25 → T26 → T27 → T28 → T29 | P1 위험 제거 | 범위 밖 쓰기·참조 순환·host 종료 오류·graph 핵심 누락·mock 사전 검사 해결 |
| 2 | T30 → T31 → T32 | 생성·취소·재시도·화면 수명 통합 | 새 child 세대·override·공통 root/preview 계약을 실제 consumer로 증명 |
| 3 | T33 → T34 | strict 테스트 경험 완성 | live effect 실행 전 차단, generated mock의 안전한 reset |
| 4 | T35 → T36 → T37 → T38 | 컬렉션 계약·디버거·성능 완성 | key/binding/trace identity 정렬 및 포화 상태 성능 검증 |
| 5 | T39 → T40 → T41 | Doctor·Fix-it·소비자 검증 | 진단→적용→graph diff→실제 build→2회차 무변경까지 연결 |
| 6 | T42 | 전체 재감사·candidate 확정 | 모든 필수 계약과 새 반례를 동일 candidate에서 다시 검증 |
| 7 | T43 | 별도 승인 후 release 절차 | RFC/병합/정확한 tag·revision의 publication gate 완료 |

공통 의미 모델은 T28에서 정렬하고 collection metadata는 T35에서 확장한다. trace의 provider identity는 이를 재사용한다. T25의 안전한 파일 쓰기는 T39/T40의 전제이며, T26/T27/T30의 수명 모델은 T32/T37의 전제다. 마지막에 graph 추출을 바꿔 앞선 모든 gate를 다시 해석하지 않도록 한다.

후속 실행 시 각 단계는 자동 검증 checkpoint이지 사용자에게 매번 승인을 받는 중단점이 아니다. 다만 새로운 공개 API 의미 결정, 승인되지 않은 소비자 수정, merge/tag/release처럼 별도 권한이 필요한 행동은 확인 후 진행한다. 실패한 선행 계약을 완료로 표시하고 다음 단계로 넘기지 않는다.

## 3. 체크포인트별 작업

### T24 — 기준선·반례 영구화·위험 설계 확인

- [ ] HEAD/upstream/worktree, toolchain/platform floor, build 환경과 기존 변경을 기록한다. 물별은 시작/종료 status 및 관련 원본 파일 hash를 비교한다.
- [ ] 임시 probe를 적절한 runtime/macro/CLI/외부 consumer fixture로 이관한다. 실패하는 회귀는 수정과 한 검증 단위로 묶고, known-failure allowlist를 상시 green 우회로 남기지 않는다.
- [ ] prototype 단계에서 네 결정을 기록한다: 비순환 resolver ownership, 파일 경로 identity에 고정된 write/rollback, 새 child generation 재생성 API, 명시적 effect/collection metadata 및 schema 호환성.
- [ ] 문서상 완료 표를 삭제하지 않고 이 보완 작업과 연결하는 재개 기록을 후속 구현 변경으로 추가한다. G 항목은 기능 부재와 증거 부재를 구분한다.
- 완료 증거: 감사 ID 추적표, toolchain별 반례 결과, 변경 전 기준선. 임시 파일이 없어도 재현 가능해야 한다.

### T25 — migration 쓰기·rollback 경로 보호 (N02)

- [x] 최초 symlink 검사 이후의 중간 디렉터리 교체와 파일 identity 변경도 방어한다. 단순히 동일 검사를 한 번 더 추가하는 데 그치지 않고 실제 쓰기가 검증한 경계를 유지하도록 한다.
- [x] apply와 rollback을 같은 경로 보호 정책으로 실행한다. 사용자 변경을 덮지 않고 중단/복구 결과를 명시한다.
- 완료 증거: 사전 검사→폴더 교체→apply/rollback 반례에서 **외부 파일 byte 변경 0**, stale/동시 편집/중첩 repo·권한 실패 회귀 통과. 모든 시험은 임시 fixture 안에서 수행한다.

완료 기록(2026-09-07): canonical root를 열린 directory descriptor에 고정하고 각 상대 경로를 `openat(..., O_NOFOLLOW)`로 순회한다. 같은 anchored parent 안의 임시 파일을 `renameat`으로 교체하며 rollback도 동일 경계를 사용한다. `pathReplacementAfterPreflightCannotEscapeRoot`를 추가했고 Swift 6 strict/warnings-as-errors에서 migration 44 tests 및 fresh public consumer가 통과했다.

### T26 — 비순환 dependency resolver와 해제 (N01)

- [x] transient child와 Provider/Lazy 재진입에 사용되는 전체 `self` snapshot 캡처를 필요한 dependency/override context로 분해한다.
- [x] 단순 weak 전환으로 외부 Provider를 무효화하지 않는다. 컨테이너 복사·외부 handle·마지막 owner의 수명을 명시한다.
- 완료 증거: shared 대조군, transient child, Provider handle, 접근하지 않은 on-demand의 마지막 owner 해제 후 **weak 참조 nil**. 외부 handle이 살아 있는 동안 정상 resolve. Debug/Release 및 실제 생성 macro consumer 검증.

완료 기록(2026-09-07): shared factory가 transient `Provider`/`Lazy`를 받을 때 late resolver는 부모 `self` 복사본 대신 init 입력, 필요한 eager shared 값, on-demand cell, override 인자만 캡처한다. transient child builder도 동일한 dependency-only context를 사용한다. generated runtime 회귀는 부모 소멸 뒤 외부 Provider resolve, 마지막 handle 해제, transient child 부모 해제, 미접근 on-demand 해제를 검증한다.

### T27 — host 세대별 종료 callback과 정리 대기 (F03, F04)

- [x] 컨테이너와 생성 당시 close callback을 한 generation record로 보관한다. 같은 identity의 중복 start가 기존 record를 변경하지 않게 한다.
- [x] 연속 start/retry/명시적 close가 진행 중인 cleanup barrier를 공유한다. 오래된 factory가 늦게 반환한 candidate도 해당 세대 callback으로 정확히 한 번 정리한다.
- 완료 증거: A→B→C 전환에서 A close를 continuation으로 정지했을 때 C가 먼저 ready가 되지 않음; old callback 출처·정확히 한 번 close·동시 close·취소된 factory·재진입 회귀. 무한 대기하는 외부 close hook의 관찰/중단 정책도 명시.

완료 기록(2026-09-07): ready container는 생성 세대의 close callback과 함께 보관하며 동일 identity의 loading/ready 재호출은 새 closure로 record를 덮지 않는다. 독립 cleanup task chain을 start/retry/close가 공유하여 A 정리 중 B가 취소되고 C가 요청돼도 C publication은 A close 완료 뒤에만 가능하다. 늦게 반환한 취소 candidate는 자신의 callback으로 정리한다. close hook에는 안전한 강제 중단 수단이 없으므로 반환하지 않는 hook은 ownership 미확정 상태로 barrier와 명시적 close를 계속 대기시키는 정책을 공개 문서에 고정했다. strict host suite 17 tests가 callback 출처, A→B→C, 동시 close, retry 및 mounted SwiftUI 흐름을 검증한다.

### T28 — canonical wiring과 graph 계약 복구 (F01, F02)

- [x] macro/build validator/graph가 같은 factory parameter dependency 추출을 사용한다. hard/Lazy/Provider/async 구분을 보존한다.
- [x] child input ID↔parent provider ID, fixed/assisted ownership을 binding pair로 직렬화한다.
- [x] schema 호환성은 T24 결정에 따른다. 알 수 없는/손실된 metadata를 unchanged로 취급하지 않고, 의미 변경과 source 위치 변경을 분리한다.
- 완료 증거: 주입 대상 교체·child binding 교환은 `--check-contract` 실패, 단순 줄 이동은 통과. 동일 파일·별도 파일·다른 모듈의 유효 consumer와 공통 의미 fixture 검증.

완료 기록(2026-09-07): graph collector가 macro/build validator와 같은 factory-parameter parser를 재사용하고 parameter label, canonical provider ID, hard/`Lazy`/`Provider` 종류를 schema v5에 직렬화한다. fixed/assisted child provider는 canonical child-input↔parent-provider pair와 ownership을 보존하며 implicit same-name wiring은 child의 ordinary input만 기록한다. v5 loader는 이전/알 수 없는 schema와 binding 배열이 누락된 provider를 fail-closed한다. 주입 대상·deferred kind·binding 교환은 의미 diff가 검출하고 source 줄 이동은 제외한다. strict warnings-as-errors Debug/Release graph·CLI 범위 148 tests가 동일 파일, 별도 파일, target-qualified cross-module 계약을 검증했다.

### T29 — Mock 사전 검사와 생성 정확성 (F05, N04, N05)

- [x] 일반 반환·throwing·typed throws·property·generic handler의 설정 상태를 사전 검사에 연결한다. Optional nil과 미설정을 분리하고 typed error를 위조하지 않는다.
- [x] parameter token과 record field 이름을 분리해 underscore/keyword/이름 충돌을 보존한다.
- [x] generic typed throws/static property 등 미지원 조합은 원본 attribute의 안정적 진단으로 거부하며 깨진 partial conformance를 생성하지 않는다.
- 완료 증거: 누락 stub이 consumer 실행 전 실패하고 정상 설정은 통과; 지원 matrix의 실제 strict consumer compile/run, 미지원 matrix의 정확한 diagnostic. compiler-owned 추가 진단과 라이브러리 진단을 구분.

완료 기록(2026-09-07): generated mock이 property, value-returning function, untyped/typed throwing function, generic handler마다 storage와 독립된 setup state를 생성하고 하나의 `missingStubSelectors` preflight로 집계한다. Optional property/return에 명시적으로 설정한 `nil`은 누락과 구분하며 typed error를 합성하지 않는다. 이름 없는 parameter에는 conformance body에서 사용할 source identifier를 추가하고 keyword 및 call-record field identity를 별도로 보존한다. generic typed throws와 static property는 원본 `@GenerateMock` diagnostic에서 함께 거부하고 mock peer를 생성하지 않는다. Debug/Release strict macro 33 tests, strict build fixture, 실제 pass consumer 실행과 compile-fail diagnostic fixture가 통과했다.

### T30 — 취소와 새 child subgraph 재시도 (F06, G01)

- [x] 이미 취소된 waiter/prepare 요청이 새 factory를 시작하지 않게 하고, 진행 중인 다른 waiter의 shared 작업은 보존한다.
- [x] provider counter만 초기화하지 않고 실패 child 및 downstream을 한 세대로 재생성한다. 부모 의존성 중 명시적으로 상속한 것만 유지한다.
- [x] retry 중 이전 완료 응답이 새 세대를 오염시키지 않게 한다. 실패·blocked·closed·cancelled 결과를 구분하고 원본 오류 관찰 경계를 정한다.
- 완료 증거: 사전 취소 시 factory **0회**, 다른 waiter는 정상 완료, 연속 retry에서 child-local identity 새로 생성·부모 identity 유지·old cache 혼합 0. 100 waiter/close/retry 조합 회귀.

완료 기록(2026-09-07): scope 진입 시 이미 취소된 task를 continuation 등록 전에 거부하고 prepare 호출의 취소를 owner 상태와 분리된 `cancelled` 결과로 보고한다. 소유 operation 자체의 `CancellationError`도 실패와 구분해 재시도 가능 상태로 보존한다. plan의 선택 subgraph retry는 실패·취소 provider와 그 downstream만 한꺼번에 새 generation으로 전환하며 준비된 명시적 parent는 그대로 공유한다. 실행 중·닫힌 affected provider는 어떤 generation도 바꾸기 전에 거부하고, generation guard가 오래된 완료의 publication을 차단한다. strict runtime 10 tests가 사전 취소 factory 0회, shared waiter 생존, 연속 재시도의 parent/child/downstream identity, non-mutating preflight, 원본 오류 경계 및 100 waiter failure/retry/close를 검증한다.

### T31 — factory AST·입력 순서·async override 조합 (F12, N03)

- [x] `try!` 등 유효 factory 표현식의 연산자 우선순위를 생성 AST에서 보존한다.
- [x] 일반 SubContainer binding을 child 선언 순서로 생성하거나, source-visible metadata가 없으면 원본 위치의 정확한 진단을 제공한다.
- [x] override된 async factory만을 위한 on-demand dependency를 미리 평가하지 않는다. 실제 사용하는 다른 provider가 있으면 shared 초기화는 한 번이다.
- 완료 증거: 지원 factory 표현식·reordered input의 same/separate/cross-module compile; sync/async×일부/전체 override에서 미사용 생성 0회, 필요한 생성 1회.

완료 기록(2026-09-07): precedence-sensitive raw `factory:` 표현식을 single-element parenthesized AST로 보존해 `try!`와 ternary가 override `??` 아래에서 재결합되거나 거부되지 않게 했다. 전체 source validator는 child `@Input` 선언 순서를 수집해 `bindings:`의 첫 불일치 key path에 `sub.binding-order`를 보고하며, 같은 파일·별도 파일·cross-module의 올바른 순서는 실제 strict consumer에서 컴파일·실행된다. async factory의 on-demand hard dependency read는 Task의 live branch 안으로 이동해 전체 override 0회, 부분/live 조합 1회를 보장한다. strict macro/configuration, runtime, validator, compile-pass/fail fixture가 이를 검증한다.

### T32 — fixed/assisted root helper와 preview의 공통 ownership (G02)

## 5. 검증·커밋·푸시 운영

후속 실행 요청에서 커밋/푸시가 승인된 경우에만 적용한다.

1. checkpoint별 구현+회귀+관련 문서를 작은 의미 단위로 묶는다. 테스트만 존재하거나 helper만 제공하는 상태를 완료로 표시하지 않는다.
2. 관련 positive/negative 실제 consumer, strict compiler, 변경된 graph/API/docs gate와 `git diff --check`를 통과시킨다.
3. 변경 경로만 명시적으로 stage하고 `git diff --cached --check` 후 commit한다. unrelated 변경과 생성물은 보존하며 `git add -A`를 기본값으로 사용하지 않는다.
4. 원격 변경을 확인한 뒤 정상 push하고 fetch/parity 및 worktree 보존 상태를 확인한다. force push와 무단 release는 하지 않는다.
5. 성공한 push마다 위 확인을 마친 다음 `/Users/changwooson/.codex/scripts/cleanup-xcodebuildmcp-artifacts.sh --apply`를 실행한다. active build/test/compiler를 중단하지 않는다. in-scope build 종료 뒤 한 번 재시도하고 다른 build가 여전히 활성 상태면 skip을 보고한다.
6. cleanup 범위는 XcodeBuildMCP DerivedData/test-products/result-bundles로 제한한다. 회수량과 최종 여유 공간을 기록하고 repository/worktree/state/locks는 삭제하지 않는다.
7. 각 결과에 SHA·toolchain·명령·test case·원격 run·남은 gate를 남긴다. 실패한 CI나 재검증하지 않은 이전 SHA를 현재 성공으로 표시하지 않는다.

## 6. 설계 확인과 최종 반례 검토

설계 미확정 사항은 T24에서 검토 가능한 prototype과 권고안으로 제시한다. 새 공개 API spelling·schema 버전·지원 범위를 여기서 임의로 확정하지 않는다. 기존 동작을 바꾸는 선택은 사용자/maintainer가 결정한다.

- generation retry: 호출자에게 반환된 old handle의 실패/폐기 정책과 부모 공유 범위.
- strict effect: effect로 분류할 명시 metadata, 완전성을 확인할 수 없는 provider의 처리.
- collection/trace: source-visible key/identity metadata 및 schema 변경과 이전 baseline의 처리.
- reset: 진행 중 호출과 기록 세대 경계, stub 유지/전체 초기화.
- consumer verify: 사용할 scheme/destination/toolchain, 현재 권한으로 검증 가능한 앱 범위.

문서상의 체크를 모두 통과해도 다음 반례가 가능한 구현은 완료로 인정하지 않는다.

- 입력 객체가 컨테이너 내부 생성 코드에 갇히는데 factory 1회 테스트만 통과한다.
- 최초 경로 검사만 통과하고 쓰기·rollback 때 다른 경로를 따라간다.
- provider override가 live dependency를 실행하거나, retry가 old child cache를 섞는다.
- 모든 primitive helper는 동작하지만 generated mock/Overrides/root/trace 흐름에는 연결되지 않는다.
- graph/Doctor가 알 수 없는 의미나 빌드 미실행을 unchanged/healthy로 표시한다.
- 기존 baseline 또는 완료 문구만 고쳐 새 candidate 검증을 대신한다.

계획 자체의 다음 gate는 사용자 검토와 실행 지시다. 구현 완료는 T42 증거로, 실제 배포 완료는 별도 승인 후 T43 증거로 각각 판단한다. 날짜 약속보다 검증된 checkpoint를 진척 기준으로 사용한다.
