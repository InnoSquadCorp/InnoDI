# InnoDI 6.0.0 — 전체 개선 실행 계획

- 작성일: 2026-09-05
- 상태: **Implementation in progress**
- 기준 checkout: 로컬 `820fdcb`; 기존 `Derived/`, `InnoDI.xcodeproj/`는 보존 대상.
- 요구사항: [여덟 가지 개선의 완료 계약](../specs/6.0.0-excellence.md).
- 기존 릴리스 목표: [RFC 0006](../rfcs/0006-assisted-subgraphs-and-container-roles.md).
- 배포 절차: [RELEASING.md](../../RELEASING.md). 이 계획은 그 절차를 대체하지 않는다.

## 1. 작업 원칙

여덟 방향을 전부 구현 범위에 넣는다. 기능 추가만이 아니라 조합·오류·취소·이주 경험을 완료 조건으로 삼는다. API spelling, schema 번호, cache owner 구현은 아직 권고안이며 T02/T03의 검증 결과로 확정한다.

이번 문서 작성은 구현·push·배포 실행이 아니다. 추후 실행 요청을 받은 뒤 아래 순서로 진행하고, 새로운 제품 결정이 필요하면 근거를 제시해 확인한다. 범위를 임의로 축소하지 않는다.

- 기존의 네 가지 발견 사항과 public factory access diagnostic을 선행 회귀로 고정한다.
- 공유 모델과 검증 계약을 먼저 만든다. macro, build plugin, graph에서 각자 별도 의미를 재구현하지 않는다.
- 한 작업은 구현·테스트·관련 문서를 함께 완료한다. baseline만 바꿔 기존 gate를 통과시키지 않는다.
- 각 checkpoint는 독립적으로 검증 가능한 크기로 나누며, 반드시 한 checkpoint가 한 commit일 필요는 없다.
- helper/API 이름만 추가하고 실제 소비자 흐름을 수동 wrapper에 의존하는 상태는 완료가 아니다.
- source-authored nominal bridge와 컴파일 시 graph 검증을 유지한다. runtime registry로 우회하지 않는다.

## 2. 단계와 의존성

| 단계 | 목표 | 원래 개선 번호 | 작업 | 진입 / 종료 조건 |
|---|---|---|---|---|
| 0 | 기준선·회귀·설계 실험 | 선행 결함 + 전체 | T00 → T02 → T01 | 현재 상태 확정 → 최소 toolchain 실험 → 이전 세 가지 assisted 결함 수정, graph 미감지 회귀 및 핵심 설계 결정 기록 |
| 1 | 공통 계약과 선언 단일화 | 7, 6의 기반 | T03, T08 | 최소 toolchain spike → source-visible bridge·공통 provider 모델·키패스 migration 방향 확정 |
| 2 | 생성 정책과 async scope | 1, 2 | T04–T07 | 공통 모델 확정 → 생성 횟수, concurrency, prepare/cancel/retry 계약 통과 |
| 3 | 테스트·프리뷰 지원 | 4 | T11–T13 | isolation 및 override semantics 확정 → 소비자가 공개 product로 안전한 mock/preset 사용 |
| 4 | SwiftUI host와 컬렉션 조합 | 3, 5 | T09–T10, T14–T16 | 수명·선언·테스트 기반 → UI identity 및 cross-module 컬렉션 계약 통과 |
| 5 | 정적/실행 의존성 디버거 | 6 | T17–T19 | 모든 의미 모델 확정 → contract diff/why/trace를 동일 provider ID로 연결 |
| 6 | doctor·Fix-it·migration 통합 | 8, 7의 수정 경험 | T20–T22 | 안정된 API와 schema → read-only 진단부터 안전한 patch 및 consumer 검증까지 연결 |
| 7 | 실제 소비자·플랫폼·6.0 마감 | 전체 | T23 | 기능별/조합 gate 통과 → 동일 candidate의 pilot/CI/문서/API/release gate 검토 |

핵심 순서는 `기반 계약 → 생성/수명 → 사용 경험 → 디버거 → 자동 진단/이주 → 릴리스 증거`다. T 번호는 추적 ID이며 실행 순서는 위 표를 따른다. assisted 수정에 필요한 metadata 전달 가능성을 먼저 확인하기 위해 T02를 T01보다 앞서 수행한다. 그래프 스키마 설계는 단계 1에서 시작하지만 graph 기능 완료는 단계 5다. 따라서 선행 graph 미감지 이슈는 T17이 끝나기 전까지 닫지 않는다.

Mock, 컬렉션, UI 일부는 계약 확정 뒤 논리적으로 독립 진행할 수 있지만, 기본 실행은 위 checkpoint 순서로 한다. 독립 실행 시에도 같은 build.db/scratch path를 공유하지 않는다.

## 3. 체크포인트별 구현 계획

### 단계 0 — 현재 기준과 설계 위험을 먼저 고정

- [x] **T00 — 기준선 및 영구 회귀 fixture**
  - fetch 시점의 원격/로컬 parity, dirty tree, toolchain, package/platform floor를 기록한다. 기존 파일을 덮어쓰거나 checkout을 교체하지 않는다.
  - 임시 probe를 `Tests/ExternalConsumerFixtures`, macro/runtime/graph suites에 영구 fixture로 옮긴다.
  - 입력 interleaving/목록 재정렬, static·assisted closure/direct·alias escaping, 잘못된 root/chained key path, public/package 경계, typed/lifetime/isolation graph drift를 포함한다.
  - 현재 strict suite, compatibility, coverage, macro/cold/no-op build 및 생성 횟수를 기준선으로 남긴다. 당시 기록한 CI 성공을 현재 SHA의 성공으로 재사용하지 않는다.
- [x] **T01 — assisted factory 결함 및 진단 수정**
  - 입력 순서, escaping metadata, 키패스 소유 타입, 접근 수준을 올바르게 처리한다.
  - same-file/separate-file/cross-module의 유효·무효 외부 fixture를 함께 검증한다.
  - 생성 코드 내부 오류가 아니라 원본 attribute/input을 가리키는 안정적 diagnostic을 제공한다.
- [x] **T02 — 핵심 API/compiler/runtime 실험과 결정**
  - Swift 6.2와 6.4에서 on-demand storage, async scope owner, nested bridge metadata 전달, MainActor/Sendable mock의 최소 spike를 검증한다.
  - D01–D03/D07을 기록한다. 공식 API 이름·최소 OS·동기/비동기 error shape를 이 단계 전에 freeze하지 않는다.
  - 새 runtime/trace 비용 baseline과 허용 budget, 단계별 예상 작업량을 이 단계 이후 산정한다. 검증 전 임의 날짜를 완료 약속으로 제시하지 않는다.

### 단계 1 — 공통 provider 계약과 선언 단일화

- [x] **T03 — canonical provider 모델과 schema 설계**
  - `InnoDICore`, `InnoDIWorkspaceAnalysis`, build support, graph의 identity/type/input-kind/lifetime/initialization/isolation/effect/contribution/source-location 모델을 정렬한다.
  - source location은 진단용 metadata와 의미 diff identity를 구분한다. 줄 이동만으로 계약이 깨지지 않게 한다.
  - JSON schema v4로 확정했다. v3/unknown/malformed 입력은 diff에서 fail-closed하며 같은 도구로 baseline을 재생성한다. source 줄/열은 진단 metadata이고 의미 diff identity에서는 제외한다.
  - parser가 모르는 실제 Swift assignability를 성공한 것처럼 추정하지 않는다. compiler 검증과 preflight 검증의 책임을 나눈다.
- [x] **T08 — factory 입력 단일 원천과 typed bridge**
  - 컨테이너의 입력 선언에서 static/assisted 분류·타입·escaping·접근성을 유도한다.
  - 별도 파일에서도 보이는 nested factory 선언은 보존한다. macro 전달이 최소 toolchain에서 불가능하면 deterministic source generator와 stale-check를 사용한다.
  - 문자열 member bridge를 키패스 기반으로 개선하고 구형 spelling의 이주 경로를 준비한다.
  - 입력 추가/삭제/rename과 생성 2회 차이 0을 검증한다. Fix-it의 실제 editor/CLI 연결은 T21에서 마무리한다.
  - child `@Input` 선언이 타입, source order, escaping, actor/access 계약의
    단일 원천이며 source-visible key-path partition은 stale edit를 즉시
    진단한다. 반복 macro expansion byte equality와 add/delete/rename stale
    partition 회귀를 `AssistedFactoryMacroTests`에 고정했다.

### 단계 2 — 생성과 수명

- [x] **T04 — on-demand shared와 복사 semantics**
  - 기본 eager 동작을 보존하고 명시적 on-demand 정책을 추가한다.
  - 원래 컨테이너와 값 복사본은 같은 논리 shared cache를 보며, 별도 생성한 컨테이너는 별도 cache를 갖도록 한다.
  - synchronous reentrancy/cycle, 초기화 도중 접근, override precedence를 정의하고 무한 대기·중복 생성을 막는다.
  - actor-bound non-Sendable 값을 억지로 다른 executor로 보내지 않는다. lock을 await나 사용자 factory 호출 전체에 무분별하게 유지하지 않는다.
- [x] **T05 — 선택적 prewarm 및 wrapper 조합**
  - 요청된 provider의 전이 의존성만 준비하며 unselected on-demand provider는 건드리지 않는다.
  - Lazy/Provider, input, override, fixed/assisted child와 조합한다.
  - 0회/1회/N회 생성 counter와 identity를 fixture에서 검증한다.
  - `OnDemandRuntimeTests`가 선택하지 않은 provider 0회, `Lazy`/`Provider` target 지연, override 0회, fixed child 및 assisted factory static binding의 단일 identity를 검증한다.
- [x] **T06 — async owner와 준비 상태**
  - InnoDI가 만든 비동기 작업의 owner를 명시하고 selected prepare의 상태/오류 provenance를 제공한다.
  - 공유 작업과 각 waiter의 생명주기를 분리한다. 사용자 서비스 내부의 별도 작업은 자동 관리한다고 주장하지 않는다.
  - root→child scope, 실패 provider와 downstream 대기, 부분 성공을 구조적으로 보고한다.
  - `DIAsyncScope`와 validated `DIAsyncPreparationPlan`이 stable provider ID, generation, bounded error type provenance, selected transitive 준비와 blocked downstream report를 제공한다.
- [x] **T07 — 취소·종료·재시도**
  - waiter 취소는 그 대기만 종료하고, 명시적 owner 종료는 소유 작업을 취소한다. 종료 후 새 작업은 시작하지 않으며 종료는 멱등적이다.
  - 재시도는 새 child generation으로 수행한다. old/new local cache를 섞지 않고 부모로부터 명시적으로 물려받은 의존성은 보존한다.
  - close/resolve race, 오래 걸리는 factory, 실패와 취소 경쟁, 외부 참조 잔존을 검증한다. 협조하지 않는 외부 작업을 강제 종료한다고 보장하지 않는다.
  - `DIAsyncScopeTests`가 waiter 취소 격리, 멱등 close, close 후 resolve 거부, 실패 후 clean generation retry, malformed plan fail-closed를 continuation 기반으로 검증한다.

### 단계 3 — 테스트를 일급 사용 경험으로 제공

- [x] **T11 — Sendable / MainActor mock**
  - isolation과 protocol/public/package 접근 수준을 보존한다.
  - concurrency-safe 호출 기록·snapshot·reset을 설계한다. unchecked conformance만 붙이는 구현은 허용하지 않는다.
  - 상속/associated type 등 여전히 지원하지 않는 표면은 지원 matrix와 진단으로 명시하며 partial conformance를 만들지 않는다.
  - `Sendable` protocol은 `InnoDITesting.DIConcurrentValueBox` 기반 immutable storage를 생성하고 compiler가 인자/결과의 Sendable을 검증한다. protocol-level `@MainActor`는 mock class에 보존하며 custom/개별 global actor, Sendable generic requirement는 fail-closed한다.
- [x] **T12 — typed throws와 테스트 실패 보고**
  - throws(E) signature와 handler를 유지하고 누락 stub/예상하지 않은 호출을 테스트 친화적으로 보고한다.
  - 임의의 E를 만들 수 없는 경우 사전 stub 검증에서 테스트 operation을 차단한다. typed throws를 지키기 위해 오류를 위조하거나 production fallback을 실행하지 않는다.
  - 동시 100회 호출 및 적용 가능한 sanitizer 검증을 수행한다.
  - `throws(E)`는 `Result<T, E>?`로 보존하고 `missingStubSelectors` 사전 검증과 `recordedCallCounts` 사후 검증을 제공한다. strict external fixture가 병렬 100회, typed failure/success, 누락 stub 차단을 컴파일·실행한다.
- [x] **T13 — 공개 테스트 product와 preset/preview**
  - 후보 `InnoDITesting` 등 공개 product를 기존 내부 `InnoDITestSupport` target과 분리한다. 최종 이름은 D06에서 결정한다.
  - typed override preset의 명시적 결합 순서와 opt-in strict effect profile을 제공한다.
  - 테스트/프리뷰 별 preset 격리를 증명한다. 기존 인스턴스의 내부 의존성을 소급 바꾸는 TaskLocal 기능으로 대체하지 않는다.
  - production product에 Swift Testing/SwiftSyntax 의존성을 추가하지 않는다. 새 공개 product를 API/coverage/doc gate에 등록한다.
  - 공개 product 이름은 `InnoDITesting`으로 확정했다. typed preset은 left-to-right later-wins이며 전역/TaskLocal state가 없다. strict/recording interaction profile, 공개 API baseline, 85% coverage floor, 독립 DocC catalog와 외부 consumer dependency를 등록했다.

### 단계 4 — 화면 수명과 확장 컬렉션

- [x] **T09 — SwiftUI container host 및 assisted root**
  - fixed/assisted child 공통 호스트를 제공한다. 후보 이름은 예시일 뿐 아직 공개 API를 확정하지 않는다.
  - lazy owner construction을 통해 body/initializer 재평가 때 버려질 child도 만들지 않는다.
  - route/document/window identity와 실제 owner 종료를 연결한다. onDisappear만으로 영구 scope 종료를 판단하지 않는다.
  - loading/failure/retry UI는 앱이 구성할 수 있게 하고 InnoDI는 일관된 상태/수명만 제공한다.
  - `DIContainerHost`와 공개 `DIContainerHostOwner`가 fixed/assisted factory closure를 같은 lazy owner로 수용한다. identity 교체 시 이전 generation을 닫고, explicit lifecycle handle만 영구 close를 수행한다.
- [x] **T10 — UI lifecycle 및 첫 소비자 전환**
  - 100회 redraw, identity 교체, 빠른 push/pop, 동일 payload 다중 창, 닫기/재진입, 취소 중 전환을 실제 hosted SwiftUI 테스트로 검증한다.
  - InnoSample People flow의 수동 State 래퍼를 공식 host로 대체하는 pilot을 준비한다. 앱 파일 수정은 실행 시 scope/dirty tree를 확인한다.
  - 생성 counter, weak-reference 해제, async task 종료를 검증한다. 단순 View typecheck를 lifecycle 검증으로 보고하지 않는다.
  - `DIContainerHostLifecycleTests`가 실제 `NSHostingView` 100회 redraw, identity 교체, 동일 payload 독립 owner, close/reentry, failure/retry, 전환 중 cancellation을 실행한다. InnoSample pilot은 T23의 exact candidate consumer gate에서 확인한다.
- [x] **T14 — assignability와 명시적 empty**
  - concrete contributor를 existential collection으로 변환하는 합법적 Swift 구성을 허용한다.
  - typealias 문자열을 같게 만드는 방식이 아니라 compiler typed witness로 실제 assignability를 검증한다.
  - malformed contributor와 명시적 empty를 구분하고 기존 배열 순서/override semantics를 보존한다.
  - `@Multibinding([])`을 explicit empty로 허용하고, generated Swift array를 compiler assignability witness로 사용해 concrete-to-existential 변환을 검증한다.
- [x] **T15 — keyed map과 provider collection**
  - 정적으로 표현 가능한 키 집합을 정의하고 중복을 reject한다. dynamic/computed key의 허용 여부는 명시적으로 진단한다.
  - provider collection 선택 시 명시적으로 eager인 의존성을 제외한 미선택 on-demand 항목이 생성되지 않게 한다.
  - 배열 order와 map key identity를 graph 계약에 반영한다. map iteration order를 플랫폼 우연성에 맡기지 않는다.
  - `DIKeyedCollection`은 source-order iteration과 duplicate-key rejection을 계약화한다. provider variants는 선택한 index/key의 closure만 실행한다.
- [x] **T16 — cross-module 명시적 합성**
  - 선언한 group/import만 합성하고 배열의 병합 순서, map collision 규칙을 고정한다.
  - 모듈 출력의 collection contract를 consumer가 검증하는 방식을 D05에서 검증한다. binary-only dependency 지원/진단 경계도 정한다.
  - separate-file, source dependency, module dependency의 중복 키/순환 결합/미가시 타입 fixture를 추가한다.
  - `DICollectionGroup.compose`와 keyed compose는 호출자가 지정한 module 순서만 합친다. `collection-cross-module` 외부 fixture가 두 source module의 existential 출력, empty, order, nested collision을 컴파일·실행한다. binary-only module도 동일 public nominal contract를 내보낼 때 소비 가능하며 자동 discovery는 지원하지 않는다.

### 단계 5 — graph와 실행 trace를 한 디버거로 연결

- [x] **T17 — provider-level graph와 의미 diff**

## 4. 기능 조합 검증 matrix

| 조합 | 반드시 증명할 내용 |
|---|---|
| on-demand × override | override한 provider의 원래 factory 실행 0회 |
| on-demand × 값 복사 × 별도 컨테이너 | 복사본은 동일 identity, 별도 생성은 독립 identity |
| prewarm × partial graph × failure | 요청 범위만 준비하고 부분 실패 원인을 정확히 보고 |
| async shared × 다중 waiter × 취소 | waiter 취소 격리, owner 종료 시 소유 작업 취소 |
| async 실패 × retry × downstream | 새 generation에서 일관된 재생성, 이전 local cache 혼합 없음 |
| assisted × closure × cross-module | 함수/alias/접근 수준/actor 및 입력 순서 계약 유지 |
| SwiftUI redraw × assisted × on-demand | 임시 child까지 포함하여 불필요한 생성 0회 |
| 다중 window × preview preset × close | 인스턴스/override/작업 수명 격리 및 종료 후 해제 |
| concrete collection × map × 모듈 합성 | compiler assignability, 결정적 key/order, 중복 key 거부 |
| provider collection × initialization policy | 선택이 미선택 on-demand 생성을 유발하지 않음 |
| Sendable mock × 병렬 호출 × typed throws | race/기록 유실/오류 타입 손실/컨텍스트 누출 없음 |
| graph contract × source 이동 × schema | 의미 변경은 실패, 비의미 이동은 통과, 미지원 schema는 명시적 실패 |
| trace × secret canary × disabled build | 입력/토큰 누출 없음, bounded 기록, 비활성 기록/할당 없음 |
| doctor × dirty tree × stale patch × 중도 실패 | 읽기 모드 무변경, 사용자 변경 보존, 적용 복구 및 두 번째 diff 0 |

동시성 테스트는 임의 sleep 대신 barrier/continuation/제어 가능한 clock과 bounded timeout을 사용한다. sanitizer는 지원되는 target/환경에서 실행하고 미실행 이유를 기록한다.

## 5. 검증과 커밋/푸시 운영

### 각 checkpoint

1. scope와 기존 변경 확인 → 관련 테스트·구현·문서의 최소 변경.
2. macro expansion과 실제 Swift consumer compile을 별도로 검증. graph/build semantics 변경에는 공통 fixture를 추가.
3. strict concurrency + warnings-as-errors, `git diff --check`, 관련 docs/API/schema gates.
4. 진행표에 코드 SHA, 실제 테스트 case, 명령, toolchain, 결과, 남은 gate를 기록.
5. 커밋/푸시 실행 요청 범위에서는 변경 경로를 명시적으로 stage하고 `git diff --cached --check` 후 commit. `git add -A`를 기본값으로 사용하지 않는다.
6. fetch/reconcile 후 정상 push, 다시 remote parity 및 worktree 보존 상태 확인. unrelated 변경은 남겨 둔다.
7. 성공한 push마다 parity 확인 후 `/Users/changwooson/.codex/scripts/cleanup-xcodebuildmcp-artifacts.sh --apply` 실행. active build를 중단하지 않는다. in-scope build 종료 뒤 1회 재시도하고 여전히 다른 build가 활성 상태면 skip을 보고한다. 정리 범위는 XcodeBuildMCP DerivedData/test-products/result-bundles뿐이며 회수량과 최종 여유 공간을 기록한다.

commit은 `feat`/`fix`/`test`/`docs`를 의미 단위로 나누되 회귀 테스트만 실패하는 checkpoint를 완료 commit으로 취급하지 않는다. source와 consumer가 별도 repo이면 각각 SHA와 검증 상태를 기록한다.

## 6. 재검토가 필요한 조건

- 최소 toolchain에서 source-visible bridge를 만들 수 없다면 generator+check 대안을 먼저 검증한다. source/type 계약을 없애는 runtime 우회는 하지 않는다.
- 기능 지원을 위해 OS/toolchain floor 상승, unchecked concurrency, graph 검증 축소가 필요해 보이면 대안과 영향을 먼저 사용자에게 보고한다.
- binary-module metadata, typed missing-stub, cancellation owner에서 반례가 나오면 해당 계약과 테스트를 보강한다. 어려움만으로 항목을 삭제하지 않는다.
- 세 소비자 중 하나가 legacy migration 때문에 막히면 선행 migration·권한·추가 비용을 별도 작업으로 드러낸다. 다른 소비자로 임의 대체해 완료 처리하지 않는다.
- 모든 여덟 항목과 조합 계약이 충족되기 전에는 이 프로그램을 완료로 표시하지 않는다. 기간보다 검증된 checkpoint를 진척 기준으로 사용한다.
