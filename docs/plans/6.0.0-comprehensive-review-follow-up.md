## 1. 목표와 기준 사실

목표는 세 가지 확정 결함을 정상·실패 대조군으로 막고, 미확정 후보와 선택적 개선을 분리해 처리한 뒤 같은 최종 후보의 검증 증거를 모으는 것이다. 새 기능을 무제한 추가하는 계획이 아니다.

2026-09-23 직전 검토의 증거를 재사용한다. 이번 계획 작성에서 테스트/원격 CI를 다시 실행한 것으로 표현하지 않는다. 작성 시 로컬 후보 HEAD와 clean 상태는 다시 확인했다.

- 확정 결함: API 계약 정규화 누락, metadata cache의 stale success, 깊은 async preparation graph의 native crash.
- 현재 후보 전체 strict tests 1,190개/99 suites, 예제 8개, 문서 Swift snippets 21개 통과. 기존 API baseline/trace budget도 통과했지만 위 반례는 검출하지 못했다.
- 미확정 후보: Doctor/외부 도구의 자손 프로세스 종료·대량 로그·권한 경계. 실패 영향은 아직 재현하지 않았다.
- 선택적 개선: 영구 close된 DIAsyncScope가 더 사용할 수 없는 factory capture를 해제하는 수명 계약.
- 원격 Exhaustive는 dependency fetch 실패, macro budget은 Swift 6.3.3 기준 대 6.4 도구체인 불일치, Mulbyul은 제거된 `@Provide(.input)` 사용으로 실패했다.
- SECURITY의 4.x 지원 문구와 공개 stable 5.1.0 사이 정책 정합성 확인이 남아 있다. 문구 수정 승인은 별도다.

이번 감사의 F01/F02/F03/U01/O01/G01–G04는 과거 문서의 같은 이름과 혼동하지 않도록 이 문서에서 **CR-** 접두어로 참조한다.

## 2. 권한·제외 범위·결정

- 이번 요청에서는 계획 문서만 작성한다. 제품 소스/테스트 수정, dependency 변경, CI 재실행, commit/push, merge/tag/release를 수행하지 않는다.
- 후속 구현은 InnoDI에 한정한다. 소비자는 **Mulbyul만**, 원본 소스·설정·pin·생성물·dirty 상태 무변경을 유지한다. committed revision을 격리 복제하고 후보 dependency만 검증 사본에 주입한다. 그 사본에도 앱 소스 migration을 적용하지 않는다.
- 물별 build를 녹색으로 만들기 위한 deprecated API 복구, 모호한 ownership 자동 결정, 소비자 source 수정은 이 계획에 포함하지 않는다.
- 최소 Swift/OS 상승, validation opt-out, `unchecked Sendable` 우회, 성능/coverage 기준 완화, 실패 숨김, source 대신 baseline만 갱신하는 방식은 제외한다.
- 실제 UI renderer/실기기 조합, 모든 filesystem/전원 장애, 전체 입력 공간 fuzzing은 기존 M01–M24의 명시적 제한을 유지한다. 새 결함과 직접 연결되면 영향 범위를 갱신하되 조용히 범위를 늘리지 않는다.

### T56 — 재현을 회귀 계약으로 옮길 준비

- 실행 시작 시 fetch 후 HEAD/branch/원격 차이와 dirty 상태를 확인한다. drift가 있으면 c7 증거를 새 후보의 증거로 재사용하지 않는다.
- 기존 검토 폴더의 반례를 해당 test target에서 실행할 수 있는 fixture로 정리한다. baseline·toolchain·명령·예상 exit를 보존한다.
- native crash 재현은 자식 프로세스에서 실행해 테스트 runner 자체를 종료하지 않는다. 시간·자원 한도를 둔다.
- 수정 전 실패를 확인하되 실패 테스트만 공개 브랜치에 먼저 push하지 않는다. 회귀와 수정은 통과하는 단위로 묶는다.

### T57 — content 기반 검증 cache

- 대상: `Sources/InnoDIBuildSupport/ValidationSignature.swift`, coordinator cache 경로/metrics, `ValidationCoordinatorCacheTests.swift`.
- **요구 CR-FR01 / 인수 CR-AC01:** 동일 경로의 같은 byte 길이·복원된 mtime, atomic replace, 동일 inode 재작성에서 content 변경을 검출한다. 실제 coordinator의 custom-init fixture가 cached/fresh 모두 동일 오류를 반환한다.
- parse에 사용한 바이트와 digest의 연결을 유지한다. 판독 중 변경·파일 삭제·읽기 실패 시 오래된 성공을 게시하지 않고 재시도하거나 명시적으로 실패한다.
- unchanged source는 content 확인 후 AST 재사용 가능. comment-only 수정, rename/delete, corrupt cache, parallel coordinator 회귀를 포함한다. cache schema/metrics 의미가 바뀌면 구버전 cache를 안전하게 무효화하고 문서도 갱신한다.
- cold/warm 및 다수 파일에서 판독 byte 수·hash/parse count·wall time을 비교한다. 정확성을 회복한 뒤 성능을 측정하며 metadata-only skip으로 회귀시키지 않는다. 기존에 없는 성능 목표는 측정 전 숫자를 발명하지 않고 T62에서 검토한다.

### T58 — 실제 source compatibility를 보존하는 API gate

- 대상: `Tools/check-public-api.py`, `Tools/tests`, `PublicAPIContractTests.swift`, `Tools/public-api-baseline.json`.

- before/after consumer를 모두 컴파일하고 전체 normalized product graph/CLI gate의 판정을 확인한다. consumer 실패뿐인데 normalizer는 동일한 반례가 다시 남지 않아야 한다.
- internal name/문서/위치/whitespace 등 비의미 변화는 통과하고, 기존 default-argument·macro signature omission·generic constraint 회귀는 유지한다.

### T59 — 준비 그래프의 call-stack 의존 제거

- 대상: `Sources/InnoDI/DIAsyncScope.swift`, `DIAsyncScopeTests.swift`, `DIAsyncRetryTransactionTests.swift`.
- **요구 CR-FR03 / 인수 CR-AC03:** empty/single/diamond/wide DAG 및 깊이 1,000·20,000의 valid graph가 생성된다. self-cycle·깊은 back edge·누락/중복 provider는 기존 오류 계약에 따라 거부한다.
- 선언 순서 기반의 결정적 topological order와 cycle path 진단, transitive selection, 역순 close를 유지한다. 목표 복잡도는 graph traversal 기준 O(V+E), heap 상태 O(V+E) 이내다.
- Debug와 optimized configuration에서 실제 runtime 소비자 fixture를 실행한다. 1k/5k/20k 입력의 시간·메모리를 기록하고 기존 retry transaction/cancel/close 테스트를 다시 실행한다.
- 실패 복구는 NSError 변환이나 crash 무시가 아니라 정상 error 또는 올바른 graph construction이어야 한다. 새 입력 제한이 필요하면 D-C03 결정으로 분리한다.

### T60 — 외부 프로세스 자원 경계 검증부터

- 대상: Doctor verification runner, Graphviz runner, 각각의 integration tests. U01을 보안 취약점으로 선결론 내리지 않는다.
- **요구 CR-FR04 / 인수 CR-AC04:** 격리 fake builder로 정상/nonzero exit, timeout 직전 완료, TERM 무시, 자손 생성, 대량 stdout/stderr, caller cancellation, umask 002/077을 검사한다. 기능에 없는 취소 인터페이스는 N/A 사유를 남긴다.
- timeout/clock을 test seam으로 주입해 300초를 매번 기다리는 시험을 만들지 않는다. 자신이 생성한 프로세스 집합만 추적·정리하며 기존 사용자의 Xcode/compiler를 종료하지 않는다.
- 확정된 누락은 owned process/group lifetime, bounded capture, private 임시 파일, timeout/exit/truncation 진단으로 보완한다. 현재 보고서의 마지막 16 KiB 계약과 실제 메모리/디스크 상한을 구분한다.
- 로그 tail만 자르는 사후 처리는 bounded capture로 인정하지 않는다. 입력량보다 보유량이 일정한 스트리밍/순환 방식을 우선 검토하고, 제한값·overflow 동작·cleanup grace를 구현 전에 명시한다. 자손 격리의 플랫폼 제약은 실제 재현으로 검증한다.
- 실험이 기각하면 근거를 남겨 종료한다. 미재현 상태면 제품 결함 수정 완료로 표시하지 않고 T65에 조건과 필요한 추가 검증을 전달한다.

### T61 — 영구 close 시 capture 해제 (선택적 개선)

- **요구 CR-FR05 / 인수 CR-AC05:** idle/ready/failed 상태에서 close 후 scope 객체가 남아 있어도 factory-only token이 해제된다. 반복 close는 멱등이고 재호출/재시도는 계속 거부된다.
- closed state 전이를 먼저 확정하고 scope-owned closure 보유를 해제하는 수명 모델을 정의한다. running task는 자신의 실행 capture를 operation 종료까지 보유할 수 있음을 문서화한다.
- running close, 늦은 결과, 다중 waiter, cancellation, retry reservation과의 interleaving을 명시적 barrier로 검증한다. sleep 길이를 늘려 통과시키지 않는다.
- 사용자 cleanup closure가 실행 중이라는 이유로 임의 강제 해제하거나 generation/transaction 의미를 바꾸지 않는다. API 계약 문서와 weak-token 회귀를 같은 변경으로 묶는다.

### T62 — CI·성능·지원 정책의 실패 상태 해소

- **요구 CR-FR06 / 인수 CR-AC06:** 승인된 후속 실행에서 적합한 기존 baseline compiler로 macro 성능을 측정하고 unchanged threshold에서 통과해야 한다. compiler provenance가 다르면 미충족으로 유지한다. toolchain 설치/지원 범위 변경이나 baseline 갱신이 필요하면 비용·사유·비교 증거와 별도 승인을 받는다.
- **요구 CR-FR07 / 인수 CR-AC07:** GitHub 계정/target SHA 확인 후 새 후보 CI 또는 승인된 실패 job 재실행을 확인한다. 네트워크 실패가 반복되면 제한된 dependency fetch retry/cache 개선을 별도 diff로 검토하되 assertion/compile 실패까지 재시도로 덮지 않는다.
- **요구 CR-FR08 / 인수 CR-AC08:** SECURITY 지원 정책을 maintainer가 결정한다. 적용 시 해당 skill의 exact-diff 승인 절차를 따르고 RELEASING/공개 stable·6.0 candidate 상태를 분리한다. 승인되지 않으면 G04를 열어 둔다.
- remote API gate가 양 compiler에서 통과해야 한다. failed/skipped 후속 성능 단계는 반드시 실제 실행 결과를 확보한다. 기존 PR CI와 실제 Release Gate dispatch를 혼동하지 않는다.

### T63–T65 — 같은 후보의 전체 검증과 인계

- **요구 CR-FR09 / 인수 CR-AC09:** 모든 필수 증거는 최종 candidate SHA와 toolchain에 묶고, 이후 변경이 생기면 영향받은 검증을 재실행한다. 마지막 문서-only commit도 전체 gate가 요구하는 exact SHA 증거 조건을 충족해야 한다.
- **요구 CR-FR10 / 인수 CR-AC10:** Mulbyul 원본의 HEAD/status/track diff/untracked hash가 보존된다. 격리 소비자가 실제 컴파일하는 InnoDI Sources와 candidate의 일치를 증명한다. Doctor와 build 결과를 별도로 기록한다.
- Mulbyul에서 `@Provide(.input)`나 ownership ambiguity가 남으면 실패 그대로 보고한다. 이 제약 아래서는 **InnoDI 수정 검증 완료**와 **물별 채택 차단**이 동시에 참일 수 있다. 소비자 migration은 별도 사용자 결정이며 테스트-only 제약으로 자동 승인되지 않는다.
- M01–M24 전체를 다시 닫되 증거 없는 행을 PASS 처리하지 않는다. 확정 결함은 재현이 사라지고 정상 대조군/회귀가 통과해야 해결이다. 미확정·선택적·정책·환경 항목은 별도 상태를 유지한다.

## 5. 커밋·푸시와 복구 운영 (별도 실행 승인 시)

1. T57/T58/T59는 각각 수정·회귀·문서의 작은 의미 단위로 검증한다. T60/T61 변경도 서로 분리하고 CI·성능·정책 변경을 대형 commit에 섞지 않는다.
2. 테스트와 `git diff --check`를 통과한 정확한 경로만 stage한다. unrelated dirty/untracked 파일을 포함하지 않고 `git add -A`, force push를 사용하지 않는다.
3. commit/push가 승인되었으면 해당 checkpoint를 순차 게시하고 remote parity와 원본/worktree 보존을 확인한다. 로컬 `origin`이 원본 저장소를 가리킬 수 있으므로 실제 GitHub remote를 먼저 검증한다.
4. 성공한 push마다 parity 확인 후 `/Users/changwooson/.codex/scripts/cleanup-xcodebuildmcp-artifacts.sh --apply`를 실행한다. active build를 종료하지 않으며 지정된 DerivedData/test-products/result-bundles만 대상으로 한다. 필요 시 in-scope build 종료 뒤 한 번 재시도하고 skip/회수량/최종 여유 공간을 보고한다.
5. 회귀가 생기면 후속 수정 또는 명시적 revert diff로 복구한다. 사용자 변경을 reset/checkout으로 되돌리지 않는다. cache format 변경은 versioned invalidation으로 복구하고 repository 전체 cache 삭제로 문제를 숨기지 않는다.
6. merge/tag/public release는 이 순서의 자동 다음 단계가 아니다. 별도 승인과 실제 Release Gate 결과를 요구한다.

## 6. 완료 판정과 계획 반례 점검

다음 구현은 문서상 일부 항목을 만족해도 완료로 인정하지 않는다.

- size/mtime에 inode만 더하고 같은 inode의 content 변경을 놓치는 cache.
- API 정규화 unit test만 바꾸고 실제 소비자 break/전체 gate를 검증하지 않는 수정.
- 20k valid graph는 통과하지만 깊은 cycle에 재귀가 남거나 선언 순서가 바뀌는 수정.
- 직접 PID만 사라지고 자신이 띄운 child가 남거나, 로그를 전부 저장한 뒤 tail만 잘라 자원 한도를 주장하는 runner.
- idle capture만 해제되며 running close·waiter·retry 경계가 깨지는 scope.
- baseline을 덮어써 성능을 통과시키거나, 실패한 물별 source를 수정해 테스트-only 제한을 우회하는 검증.
- 이전 SHA 테스트/PR CI를 최종 exact SHA 또는 공개 6.0.0 배포 증거로 사용하는 보고.

**구현 검증 완료:** CR-F01–F03 해결, 승인된 개선 회귀 통과, U01 판정과 제한 공개, 필수 library gate 충족.
